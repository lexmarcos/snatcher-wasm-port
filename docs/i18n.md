# Translation (pt-BR)

The game text can be shown in Brazilian Portuguese. English stays the default: with the language set to English every output of
the engine is byte-identical to the original (tests: `engine/tests/i18n.rs`, `player_path`, `prompts`).

## How to use it
1. Build once: `scripts/build-web.sh` (it runs `snt i18n-build i18n/pt-BR i18n/build/pt-BR.pack`).
2. Serve: `bun web/server.ts` (it serves `/i18n/pt-BR.pack` and `/i18n/pt-BR/ui.json`; restart a server started before this feature).
3. Open `http://localhost:5300/?lang=pt-BR` or pick **Idioma / Language** in the start overlay or in the menu (Esc). The choice is
   stored in `localStorage` (`snatcher.lang`); `?lang=` overrides it for that visit. It can change during play: the next message or menu is drawn in
   the new language. Debug jump example: `?lang=pt-BR&scene=SP06:0`.
4. Native runs: `I18N_PACK=i18n/build/pt-BR.pack cargo run --release -p snengine --example run -- ...`.

## Files
| path | content |
|---|---|
| `i18n/pt-BR/SPxx.json` | one per script file: `"<offset>": {"h": "<hash of the English string>", "t": "<markup text>"}` |
| `i18n/pt-BR/names.json` | speaker names by speaker number (`snt i18n-names assets/raw/files` lists them) |
| `i18n/pt-BR/ui.json` | strings of the web page (keys = `UI_EN` in `web/src/i18n.ts`; test `web/test/i18n.test.ts`) |
| `i18n/pt-BR/GLOSSARY.md` | glossary, style guide and the record of non-literal adaptations |
| `i18n/build/pt-BR.pack` | generated, not committed |
The English text is **not** stored in the repository: the tools read it from the user's `assets/raw/files` and compare the FNV-1a hash.

## Markup
Printable ASCII and the pt-BR letters are themselves. `{nl}` new line (F2), `{page}` page break (F6), `{auto}` auto-advance (F4),
`{c0}`..`{c6}` colours (F8..FE, `{c1}` normal, `{c2}` button names, `{c3}` key information, `{c4}` alert, `{c6}` narration/caption),
`{btn:EC}` `{btn:EE}` `{btn:F0}` button placeholders (shown as the button icon / letter), `{lb}` `{rb}` literal braces, `{xNN}` any other byte.

## Font
The 102 original glyphs are untouched. Glyph codes 0x86-0xA5 are the button icons, **0xA6-0xC5 are the pt-BR glyphs**
(`core/src/i18n.rs` `PT_GLYPHS`): á à â ã é ê í ó ô õ ú ü ç, the capitals Á À Â Ã É Ê Í Ó Ô Õ Ú Ü Ç, º ª « ». Curly quotes were not added
(use `"` and `'`). `snt i18n-sheet assets/raw/files out.png "text"` renders a sample with the real font and widths.

### Dialogue and menu layouts (branch `pt-line-spacing`)
In pt-BR the dialogue windows use a **10 px line pitch** and the accented capitals are the **exact original capitals plus an accent above**; menus keep
the 9 px pitch and the compact capitals (approach B, below). English never changes. The two layouts are chosen per window, as follows.

| window | layout | reason |
|---|---|---|
| message box with a name (speaker >= 2), also in the wide portrait layouts (Jordan terminal) | **10 px**, 5 lines per page | free-running text, a page break costs one button press |
| narration (speaker 1) and box without a name (speaker 0) | **10 px**, 6 lines per page | same |
| a string without a pt-BR translation (English fallback) in pt-BR mode | 9 px, original | the original text was written for 6 / 7 lines |
| command menu, CHOICE lists, Jordan database lists, investigation sub-menus | **9 px**, compact capitals, 7 lines (6 wide) | a list cannot lose a line (up to 7 items, paging arrow on the 7th), the highlight bar is a 9 px sprite tied to `y = 9 i` |
| save list, SAVE / OVERWRITE, keyboard, phone, code entry | 9 px / fixed pitch, not translated | the VM compares them with English data |

Numbers (`i18n::TALL_PITCH` = 10, `i18n::TALL_ACCENT_ROWS` = 2; `MessageBox::tall`, `TextWindow::start_with(.., tall)`; the engine switches a message to the
10 px layout when its string has a translation: `Engine::cmd_message`):

| item (10 px layout) | value |
|---|---|
| line cell | 2 accent rows + the 8 rows of the glyph cell = 10 rows (ink of a line lies in `y0 - 2 .. y0 + 7`) |
| name line | unchanged, y = 0 (no name contains an accented capital) |
| text line i, with a name | glyph rows y0 = 11 + 10 i (accent rows 9 + 10 i, 10 + 10 i), i = 0..4: **5 lines**, last glyph row 58 |
| text line i, narration / no name | y0 = 2 + 10 i (accent rows 10 i, 10 i + 1), i = 0..5: **6 lines**, last glyph row 59 |
| end of page | the original rule: the next line would start at y >= 0x39 (57), then wait for confirm; typewriter, clearing, the page marker sprite and the portrait are untouched |
| bitmap | still the 256x64 window; row 63 is the last, nothing is drawn above y = 0 |

The mission text proposed a single accent row (y0 = 10 + 10 i with a name, 1 + 10 i without). It was tried: on the original capitals (whose top row
is solid ink) a one-pixel accent cannot be told apart (acute / grave only by one column, circumflex = three pixels). The cell has room for a two-row
accent for the same 5 / 6 lines, so `TALL_ACCENT_ROWS` = 2; set it to 1 to get the single-row variant (only the lower accent row is drawn, the
lines move up by one row, the tests follow the constant).

Dialogue glyphs of the accented capitals (`i18n::TALL_CAPS`, drawn by `TextWindow::glyph` when `tall` is set): the glyph of the original capital A E I O U C
**unchanged** (rows 0..6, row 7 empty) at the line's y0, plus the accent in the two rows above (acute and grave 2-pixel diagonals, circumflex a 2-row
caret, tilde the wave of the lower-case ã, diaeresis two dots in the upper row, one blank row above the letter), and for Ç the cedilla in row 7.
Advance widths are those of the base letter. Lower-case pt-BR glyphs are the same in both layouts. The 102 original glyphs and the `PT_GLYPHS` art are untouched.

### Accented capitals in menus and the 9 px layout (measured, then drawn to fit)
Measurements (`SUBCODE.BIN` font, `core/src/actions.rs` `TextWindow` / `MessageBox`, `engine/src/menus.rs`, `engine/src/game.rs`):

| item | rows of the 8x8 cell (0 = top) |
|---|---|
| original capitals A-Z | ink in rows **0..6** (7 high), baseline = row 6, row 7 always empty |
| original lower case | x-height rows 2..6 (5 high); ascenders b d f h k l (and t from row 1) rows 0..6; descenders g j p q y reach row 7; the dots of i and j are row 0 |
| line pitch (original) | **9 px** in every text window (row 8 is never drawn: one blank row between lines) |
| message box, with name | name line y = 0, x = 0x10; text lines y = 9, 18 .. 54 (6 lines), x = 0x18 |
| message box, narration (speaker 1) / no name (speaker 0) | **first line at y = 0**, x = 0x28 / 0x18, lines up to y = 54 (7 lines) |
| command menu, choice lists, Jordan database lists | line i at y = 9 i (**line 0 at y = 0**), x = 0x10, 7 lines (6 in the wide portrait layout); the highlight bar is a 9 px high sprite (rows 0..8 of the line) |
| keyboard / phone / code entry | ASCII only, fixed pitch, never translated |
| every window | the same 256x64 bitmap; `TextWindow::glyph` clips at the top and bottom of the bitmap, nothing can be drawn above y = 0 |

In a 9 px window an accent above the cell does not fit (four window types start at y = 0; on the other lines rows -2/-1 are rows 7/8 of the previous
line, and in menus rows 0..8 are the highlight bar). **Approach B** is therefore used in menus (`TextWindow::start`, `tall` off): all pt-BR glyphs stay
inside their 8x8 cell.

Design of the compact accented capitals (`PT_GLYPHS`):
* baseline = row 6, exactly as the original capitals; row 7 stays empty (only the cedilla of **Ç** uses it);
* body 5 rows high (rows 2..6, the x-height) drawn in the style of the original capital, accent 2 rows high in rows 0..1, so the glyph spans rows 0..6;
* accents: acute and grave are 2-pixel diagonals, circumflex a 2-row caret, tilde the 2-row wave of the lower-case ã, diaeresis two dots in row 0. Over
  the narrow apex of A the acute and grave sit beside the apex;
* **Ç** is the original C (rows 0..6) plus a cedilla in row 7; advance widths are those of the base letters (A 9, E 8, I 5, O 8, U 9, C 8).

Known limitation of the compact form: the 5-row body is as high as the x-height, 2 px lower than the original capitals, so in all-caps menus an accented
letter looks a little smaller than its neighbours. That is what the 10 px dialogue layout above removes for running text.

Tests: `engine/tests/i18n.rs` `dialogue_line_positions_per_window_type` (first line Y, pitch and lines per page of every window type, 10 px and 9 px),
`tall_accented_capitals_are_the_original_capitals_plus_accent_rows` (rows 0..6 equal to the original capital, accent rows, Ç cedilla, compact form
unchanged in `start`), `no_glyph_pixel_leaves_its_dialogue_line_cell` (every glyph at every line position of every dialogue window: inside its cell,
not clipped), `accented_capitals_share_the_baseline_of_the_original_capitals` and `pt_glyphs_stay_inside_their_line_cell_in_every_window_position` (compact
forms in menus), `pt_player_path_from_the_title_to_the_first_dialogue` (title screen to the first translated message box with the real SP06 file);
`core/src/i18n.rs` `dialogue_layout_pages_and_positions`, `glyph_art_is_valid`.

## Engine
`sncore::i18n::Translation` is the pack (offset -> translated bytes per SP file, plus speaker names). `Engine::set_language(true)` /
`load_translation(pack)` (wasm: `set_language("pt-BR")`, `load_translation(bytes)`). The VM keeps using the original text offsets (menu paths, CHOICE
matching, saves); only the display side maps an offset to the translated string, which lives after the original text area
(`Translation::extend_area`). A missing entry falls back to the English string, so partial translations work. Menus that read typed text (keyboard /
keypad entry, 9 or more items: SP05 name search, SP09 code entry, ...) are never translated (`i18n-check` rejects them).

## Geometry rules (measured, `snt i18n-stats`)
* Message box: 256 px wide bitmap, text starts at x = 24 (speakers, name line at y = 0, text from y = 9: 6 lines per page in English, 5 in the pt-BR
  10 px layout), x = 40 for narration (speaker 1, 7 lines in English, 6 in pt-BR) and x = 24 without a name (speaker 0, 7 / 6). A page ends when the next
  line would start at y >= 57, then waits for confirm; more text simply continues on the next page (the engine paginates by itself: no scroll, no
  overflow). A line is cut after 50 characters. Widths do not depend on the layout.
* Limits used by the validator: line end x <= 232 (speech), 216 (narration), i.e. symmetric margins; the longest English lines end at 225 / 216.
  Menu labels: start at x = 16, at most 32 bytes, end x <= 240 (the highlight bar width); the longest English label ends at 242.
* Pages: more pages than the English string is a warning, and an error when the string has `{auto}` (timing in action scenes: a page break would
  ask for a button press in the middle of the action). A page that holds more lines than the window (5 / 6, `i18n::lines_per_page`) is an error ("page n
  is full ... run i18n-reflow"): page breaks of a pt-BR text must be explicit `{page}`, placed by `i18n-reflow` or by hand.
* Colours, `{btn:..}` and `{auto}` counts must equal the English string (colours as a sequence); `{page}` may only be added (never fewer than English),
  except in `{auto}` strings where the count must be equal.

| command | use |
|---|---|
| `i18n-ctx <files> SPnn [from [to]]` | context dump (scene, speaker, voice id, menu path, widths); `I18N_LANG=i18n/pt-BR` adds the PT line |

### Re-flow for the 10 px layout (`snt i18n-reflow`)
Fewer lines per page (5 / 6 instead of 6 / 7) make some strings longer than a page. The engine paginates an overflowing text by itself, so `i18n-reflow`
makes the break explicit and chosen. Deterministic and idempotent (a second run changes nothing); it never changes a word (it checks that the words
before and after are the same, in order) and keeps colour, button and `{auto}` tokens attached to their word (words are only split at spaces).
1. The author's `{page}` are hard breaks; only a page (the text between two `{page}`) with more than 5 / 6 lines is touched.
2. Such a page is split at the author's line breaks into the fewest pages; among those it avoids one-line pages and breaks in front of a `- ...` line,
   prefers breaks after a sentence (`. ? !`) and then evenly sized pages. If a greedy re-wrap of the real pixel widths saves a page and the author's
   breaks are only width-driven (no list, title or sentence-per-line structure) the lines are re-wrapped first.
3. `{auto}` strings never get a `{page}`: they are re-wrapped greedily into the window; one that still does not fit is listed as UNFIT and its wording must
   be shortened by hand (none was needed: the longest `{auto}` page has 3 lines).
Status of the data in this branch: see the commit "re-paginate the pt-BR text" (run `snt i18n-reflow i18n/pt-BR assets/raw/files all --dry` to check that
nothing is left to do; `i18n-check` fails otherwise).

## Deliberately not translated (counted as "not translatable / kept" in the status table)
* **SP01** is the developer debug menu (`Command Debug`: ACT1 IN, SCENE_QUEEN01, Japanese romaji such as KOUJO/TIKADO, CD-DA test, EVIDENCE pos). It is only reachable with `?scene=SP01:0`
  and has no player-facing text. It stays English; the 17 strings that are shared with real scenes (voiced lines such as "Cu...Cunningham!!") are translated through the duplicate fill.
* Entry-style menus that the VM compares with English data: SP05 name entry, SP09 code/birthmark keyboard, SP18/SP35 Napoleon password words and phone digits, SP16/SP27/SP28 "SAVE n / OVERWRITE SAVE n"
  and the answer lists (BENSON, QUEENS, ...), the SP17/SP34 turbocycle destination lists. The dialogue around them says "(em inglês)" where the player must type English.
* 8 strings in SP02 (song lyrics, a Japanese greeting, silence dots), the JUNKER/JORDAN acronym expansions (SP04, SP06, SP08@42b7), the "Face to face" memo text (kept in English quotes inside the
  translated lines) and product/venue names (Junker's Eye, liquid sky, SNOW-9, Plato's Cavern, Outer Heaven, Moonsalt).
